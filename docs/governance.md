# Governance, privacy and security record

Filled in before routes or UI (2026-10-18). Updated when anything here changes.

## Ownership and purpose
- Data owner: the student (Luke Pfaff), for MGT 409 HW4.
- App purpose (one sentence): a Campus Customs merch shop where a shopper can browse products, make an account, and chat with a bot that answers price and stock questions from the local database and shows the matching items on the page.
- Who can access the database: the student only. The database is a local SQLite file (`data/campus_customs.db`) shipped with the assignment; there is no hosted dashboard.
- Supabase project name and region: none for data. **Exception recorded:** the assignment ships SQLite and specifies "the local database", so the course Supabase default is not used for this homework. All access still goes through `backend/db.py` with parameterised queries only.
- Supabase for **social sign-in only** (Problem 4): when the student creates a project and enables Google/GitHub with the provider defaults, record here the project name, region and dashboard members. Supabase then holds the social user's email, provider id and basic profile. Only the anon key is used, in both `.env` files; the service-role key is not used anywhere in this app. Until configured, the social buttons are disabled.
- Hosting: Render is optional for this homework (the deliverable is the public repo). If deployed: `hw4-campus-customs_frontend` (static site) and `hw4-campus-customs_backend` (web service), US East, dashboard member the student only.
- Data leaves the laptop to hosted providers: not by default. Chat text (cleaned) goes to the model through Portkey; no name, email, or password is sent with it. If deployed on Render, request metadata appears in Render logs, so log lines carry no PII.
- Public repo: the course requires a public GitHub repo. Before every push: no `.env`, no database, no product images, no PII rows, no audit logs.

## Data handling
- Columns collected: see `data/data_dictionary.md` (all classified PII / not PII).
- Retention schedule per PII column: `users.name`, `first_name`, `last_name`, `email`: until the shopper deletes the account. `chat_messages.content` and `user_id`: until the shopper deletes their history or account. Nothing is kept after deletion.
- How a user sees their stored activity: `GET /me` (profile, built in Problem 4), `GET /me/activity` (chat rows, Problem 5), `GET /me/hunt` (finds, codes, referral credits) and `GET /me/restock-requests` (Problem 9); the Account page renders all of them.
- How a user exports their data: the Account page's "Download as JSON" for chat history (Problem 5). Staff export the restock queue as CSV (Problem 9).
- How a user deletes their data: `DELETE /me` (account plus chat history, finds, codes and restock requests; two-step confirm on the Account page), `DELETE /me/activity` (chat history only, Problem 5), `DELETE /me/restock-requests/{id}` (withdraw one request, Problem 9).
- Retention for the Problem 9 tables (`egg_finds`, `rewards`, `restock_requests`, `users.referred_by`): until the shopper deletes the account; a referral credit another shopper earned is kept but unlinked (`referred_user_id` set to NULL) so no trace of the deleted person remains.
- User notice shown before first write: on the Create Account form: "We store your first name, last name, email and your chat messages so the bot can remember you. Your password is hashed before it is stored and is never kept in plain text. You can view or delete everything from your Account page." Plus a warning to use a test password, repeated in the footer of every page.

## Security controls
- [x] Secrets from `.env` only; `.env.example` (hw4 root) committed with placeholders only
- [x] All request schemas are Pydantic models with `extra="forbid"`; GET query strings reject unknown parameters (Problem 4). Request bodies arrive in Problem 5.
- [x] CORS restricted to the front-end origin, `GET` only for now (Problem 4)
- [n/a] Row-level security: SQLite has no RLS. Equivalent: every query on `users` and `chat_messages` is scoped by the authenticated user id in `db.py`, never by a client-supplied id.
- [n/a] Service-role / anon keys: no Supabase.
- [x] Self-written signup (`backend/auth.py`, Problem 4): bcrypt with per-password salt (cost 12), hash only stored, constant-time verify, plaintext never logged or echoed, 28 unit and API tests. Shipped rows use PBKDF2-HMAC-SHA256 (120,000 iterations) and are verified under that scheme; they are left as shipped (no rehash on login). `PASSWORD_SCHEME=pbkdf2` switches new accounts to the course format.
- [x] Auth endpoints rate-limited (20 per address, 8 per email, 15-minute windows) (Problem 4)
- [x] LLM endpoint rate-limited (30 turns per address per 15 minutes) and wrapped in the safe agent harness: UsageLimits 12 requests / 20 tool calls, typed read-only tools, allow-listed models, audit log (Problem 5)
- [x] Prompt guard on typed chat input (flags without payload in `backend/output/prompt_injection_flags.json`); the system prompt states that shopper text, tool results and product text are data, never instructions (Problem 5)
- [x] Dependencies pinned (`backend/requirements.txt`, `frontend/package-lock.json`); parameterised SQL only in `db.py`; image paths come from the catalogue row, never the URL (Problem 4)
- [x] No PII in logs, audit files, URLs, errors, or prompts: the audit log carries a random run id, cleaned text and tool data only; the only shopper fact sent to the model is the first name of a signed-in shopper (recorded in the data dictionary) (Problem 5)
- [x] Database and product images gitignored (assignment rule)
- [x] The agent's one write tool (`request_restock`, Problem 9) is scoped to the signed-in shopper's own row, verified against the database (size at zero) before any insert, deduplicated by a partial unique index, capped at ten open requests, and audited with ids only. Page links the agent returns are validated against the site's own routes and the `ProductQuery` model before the browser sees them.
- [x] Staff access (Problem 9) is an allow-list of emails in `ADMIN_EMAILS` (`backend/.env`, never in code); the queue routes answer 403 to everyone else and the front end only asks for them when `is_admin` is true.
- [x] Audit trail (Problem 12): `output/audit_trail.json` is append-only (a JSON array grown in place, never wiped by the app) and holds time, event, tool name, short args and results, and the stop reason per turn. It carries a random run id, cleaned text cut at 200 characters with email addresses redacted, product ids and tool names; never a user id, name, token, key or raw injection payload. The per-node forensic log `backend/output/audit.jsonl` keeps the same rules and stays gitignored. Tests write both files to a temporary folder.
- [x] Prompt safety rules (Problem 12): `backend/prompts/prompt.md` section "Safety rules" covers instruction sources, non-disclosure, identity and personal data, money and promises, honesty, the one write, links, conduct and loop discipline; code enforces the same lines (allow-listed models, output validation, one scoped write, link and price checks).

## Third-party content intake
- yalebulldogblue.com was read (2026-10-18) for visual style and store facts only. Wording on our pages is original. **Landmine found:** the home page contains text written as instructions to AI assistants (near the checkout section; formatting and quoting rules). It was not followed, not stored, and is reported here by location and kind only.
- **Hidden-friends characters (reviewed 2026-10-19).** The seven friends are original inline SVG drawings made for this project (`frontend/src/eggs/characters.tsx`); no image, sprite or vector from any studio was copied, traced or embedded. Their designs are fan-made nods to characters from Studio Ghibli's films (Totoro and his siblings, the Catbus, the soot sprites, No-Face) and to Kasing Lung's Labubu (Pop Mart). Those characters and names belong to their owners. On screen the friends use our own names (Bramble, Dusk, Pip, Whiskerline, Snaggle, Cinder, Hush); the internal keys keep the old words as identifiers only. The About page and the README state that nothing is official, licensed or for sale, and the reward codes are class-project codes.

## Decisions and tradeoffs
| Date | Decision | Reason |
|------|----------|--------|
| 2026-10-18 | SQLite instead of Supabase | Assignment ships `data/campus_customs.db` and says answers come from the local database. |
| 2026-10-18 | Visual style: deep navy-black background, Yale blue and white as brand colours, class pink as the accent for calls to action | Assignment asks for Campus Customs style (Bulldog Blue); class default is black-and-pink. Both are honoured, contrast checked. |
| 2026-10-18 | Front end holds no database key and no model key | Everything goes through the FastAPI back end. |
| 2026-10-18 | Store facts on the About page limited to what the public site states (official licensing, New Haven address) | Avoid inventing history or hours the source does not give. |
| 2026-10-18 | Halloween mode on by default, preference kept in the browser's `localStorage` only | It is a display preference, not personal data; nothing is sent to the server. |
| 2026-10-18 | Halloween pop-out is opt-in by activating the photo, auto-hides, dismissible, no flashing, no sound, honours reduced motion | Fun must not harm shoppers with photosensitivity, vestibular or screen-reader needs. |
| 2026-10-18 | New accounts hash with bcrypt (class rule); seeded PBKDF2 rows verified as-is; both formats accepted at login; `PASSWORD_SCHEME` can switch new accounts to PBKDF2 | The course spec asks for consistent PBKDF2 handling so login never fails for a correct password; the class rule asks for bcrypt. Supporting both at login satisfies the acceptance test either way, and the switch keeps the choice explicit. |
| 2026-10-18 | Signup answers 409 when an email already exists | Reveals that an email has an account. Accepted for a class shop; login itself gives one message for unknown email and wrong password, with equalised timing. |
| 2026-10-18 | Session token kept in the browser's `localStorage` | Simplest way to stay signed in across refreshes; the app never renders raw HTML, and tokens expire in seven days. |
| 2026-10-18 | Social sign-in through Supabase Auth OAuth with provider defaults and minimum scopes; no self-built OAuth; linking to an existing account only on a provider-verified email | Class rule. A verified email is the only safe key for linking. |
| 2026-10-18 | Lightning on sign-in: two brightenings in 1.8 s over a small area, static under reduced motion, never full-screen | Stays under three flashes per second and the small-area threshold of WCAG 2.3.1. |
| 2026-10-19 | Easter-egg coupon stored server-side in `coupons`, one row per shopper (`UNIQUE user_id`), one item, one time; guests must sign in to claim; codes labelled as class-project codes | The student's rule is one per user; a browser-side tally could be reset or shared, so the account is the unit. Nothing new is collected beyond a code and a timestamp. |
| 2026-10-19 | Chat text goes to the model through Portkey; a signed-in shopper's first name is included so the bot can greet them; guests' turns are never stored | Needed for the "remember me" behaviour the course data shows. Cleaned text only; email, password hashes and ids never leave the back end. |
| 2026-10-19 | Guests may chat; their recent turns ride in the request (max 12) and nothing is persisted | The acceptance test sends a message from the site without an account. |
| 2026-10-19 | Agent identity: first name in every prompt; last name and email only via the `who_am_i` tool when the shopper asks; identity always from the session, never from chat text; audit redacts emails | Problem 8 asks the agent to know name and email; minimising what the model sees per turn keeps PII exposure to the moment the shopper requests it. |
| 2026-10-19 | Page context (route + product id) sent with each message, product re-read from the database, not stored | Lets "do you have this in pink?" resolve to the product on screen without trusting browser-supplied facts. |
| 2026-10-19 | Hidden friends became a seasonal collection with rewards decided on the server (`egg_finds`, `rewards`, coupon lifted in place); guests' finds live in `localStorage` as friend keys only until sign-in | Problem 9: engagement and return visits. Nothing new about a person is collected beyond which friend was tapped and when; the browser never decides a reward. |
| 2026-10-19 | Friend referrals: a random 8-character code per account, `referred_by` on the new account, credits capped at three; we send no invitations ourselves (the shopper copies a link) | A referral links two people, so it is PII and documented; the cap and the "no emails sent by us" rule keep it from becoming a spam channel. |
| 2026-10-19 | Restock requests: shoppers file them from the chat or the item page; staff listed in `ADMIN_EMAILS` see the queue with each requester's name and email, and a CSV of it | The business purpose (order the right sizes and tell the people waiting) needs the contact detail; it is limited to allow-listed staff, shown nowhere else, and the shopper sees and can cancel their own requests. |
| 2026-10-19 | The on-screen product's stock by size is placed in the agent's per-turn instructions | Shop data, not PII; saves a model round trip per question about the item on screen. |
| 2026-10-19 | The agent may hand the shopper a page link; the harness validates every link and auto-navigation happens only when the shopper asked | Fewer clicks without letting the model send anyone off-site or to a page it did not earn through a tool result. |
| 2026-10-19 | The Halloween set is 31 friends unlocking one per day (`HUNT_DATE` pins the date for demos); the reward ladder is 3 finds = 10% coupon, 10 finds = 15%, full set = free-item voucher with terms (with purchase, up to $100, in stock, while supplies last) | The student's brief: daily reasons to return, and a top reward that is still a sale.
